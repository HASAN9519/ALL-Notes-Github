LINUX SYSTEM DIRECTORIES - INTERVIEW Q&A PRACTICE
====================================================
(Companion to linux_directories_guide.txt)

SECTION 1: BASIC RECALL QUESTIONS
----------------------------------------------------

Q1: What is the difference between /bin and /usr/bin?
A: Traditionally, /bin held essential binaries needed for basic
   system operation, even in single-user mode, while /usr/bin held
   non-essential user binaries installed later. On modern distros
   (Debian, Fedora, Ubuntu), this distinction is mostly historical —
   /bin is now a symlink to /usr/bin as part of the "usr-merge".
   Interviewers ask this to see if you know the history AND the
   current reality.

Q2: Where would you look for system logs?
A: /var/log — e.g., /var/log/syslog or /var/log/messages for
   general system logs, /var/log/auth.log for authentication
   attempts, /var/log/dmesg for kernel/boot messages. On systemd
   systems, `journalctl` is also used alongside or instead of files.

Q3: What's the difference between /etc and /var?
A: /etc holds static configuration files that define how the
   system SHOULD behave. /var holds data that changes constantly
   during operation (logs, caches, spool files) — data that
   reflects what the system IS doing.

Q4: What is /proc and is it a real directory?
A: No — /proc is a virtual (pseudo) filesystem generated by the
   kernel in memory. It doesn't exist on disk. It exposes live
   kernel and process data as if they were files, e.g.
   /proc/cpuinfo, /proc/[PID]/status.

Q5: Why is /root separate from /home?
A: For reliability and security. If /home is on a separate
   partition or network mount that fails to mount at boot, root
   still needs a home directory to log in and fix the problem.
   Keeping /root under / ensures it's always available.


SECTION 2: SCENARIO / TROUBLESHOOTING QUESTIONS
----------------------------------------------------

Q6: "The server's disk is almost full. Walk me through how you'd
    find out what's eating the space."
A: Suggested approach:
   1. Run `df -h` to see which partition/mount is full.
   2. Run `du -sh /var/* 2>/dev/null | sort -rh | head` to check
      /var first (logs, caches, and package data commonly grow).
   3. Check /var/log for oversized or rotating log files.
   4. Check /tmp for leftover files not cleaned up.
   5. Check /home if user data is unexpectedly large.
   6. Use `ncdu` for an interactive breakdown if available.
   Mentioning /var/log specifically shows practical knowledge.

Q7: "A service fails to start after a reboot. Where do you check?"
A: 1. `systemctl status <service>` for the immediate error.
   2. `journalctl -u <service>` for detailed logs.
   3. /var/log/syslog or /var/log/messages for broader context.
   4. Check the service's config in /etc (e.g., /etc/<service>/).
   5. Check /etc/fstab if the failure is related to a missing
      mount point the service depends on.

Q8: "You need to mount a USB drive manually. What directory do you
    use, and why?"
A: /mnt is the conventional location for manually/temporarily
   mounting filesystems (e.g., `mount /dev/sdb1 /mnt/usb`).
   /media is typically reserved for automatic mounts handled by
   the desktop environment or udisks.

Q9: "Where would a custom, manually-installed application (not
    from a package manager) typically be placed, and why?"
A: /opt — it's meant for self-contained, third-party software
   that doesn't follow the standard FHS layout, keeping it
   separate from system-managed files in /usr so package managers
   don't conflict with it.

Q10: "The system won't boot. What directory-related things would
     you check?"
A: 1. /boot — confirm the kernel (vmlinuz) and initramfs files
      exist and aren't corrupted.
   2. GRUB config, usually under /boot/grub/grub.cfg.
   3. /etc/fstab — a bad entry here can cause boot failures if a
      filesystem fails to mount and isn't marked "nofail".
   4. Boot into rescue/single-user mode to inspect logs.


SECTION 3: CONCEPTUAL / "WHY" QUESTIONS
----------------------------------------------------

Q11: Why does Linux use a single root filesystem instead of
     drive letters like Windows?
A: Unix-style systems treat everything — including other disks,
   partitions, and even devices — as part of one unified tree,
   mounted at various points (like /mnt or /media). This makes
   the filesystem layout consistent and location-independent from
   the user's perspective.

Q12: What's the practical difference between /lib and /usr/lib?
A: /lib traditionally held libraries required by binaries in /bin
   and /sbin (needed at early boot before /usr might be mounted).
   With the usr-merge on modern distros, /lib is now a symlink
   into /usr/lib, since initramfs handles early boot needs instead.

Q13: If you were auditing a Linux system for security, which
     directories would you pay closest attention to, and why?
A: - /etc — misconfigured permissions or exposed configs
      (e.g., /etc/shadow, /etc/ssh/sshd_config)
   - /var/log — for signs of intrusion or failed login attempts
   - /tmp — often world-writable; a common target for exploits
      and privilege escalation
   - /root and /home/*/.ssh — for exposed keys or credentials


SECTION 4: RAPID-FIRE ONE-LINERS
----------------------------------------------------
(Good for quick verbal answers under time pressure)

- /etc      -> "Where configs live."
- /var/log  -> "Where logs live."
- /tmp      -> "Temporary, often wiped on reboot."
- /proc     -> "Virtual, live kernel/process info."
- /boot     -> "Kernel + bootloader files."
- /opt      -> "Third-party apps outside the package manager."
- /dev      -> "Devices represented as files."
- /home     -> "User personal data."
- /root     -> "Root's home, kept separate for reliability."
- /usr      -> "Bulk of installed software and libraries."


PRACTICE TIP
----------------------------------------------------
Try explaining each answer OUT LOUD in under 30 seconds, as if
answering live. Interviewers value clarity and practical
reasoning over textbook definitions — always try to tie an answer
back to a real command or real troubleshooting step when you can.
